# Центр мультиканального аутрича

Команда ведёт проекты, сегменты, рассылки и почтовые ящики в одном сервисе. Раздел «Базы» хранит общий каталог исходников и выборок. Приложение работает на Google Apps Script, данные хранятся в Google Диске и Google Таблицах, а GitHub Actions публикует обновления.

Порядок работы для команды — в [WORKFLOW.md](WORKFLOW.md): загрузка без ручного приведения столбцов, пополнение сегментов и проверка только новых контактов.

## Вход по закрытой ссылке

Команда открывает постоянную страницу `https://seainkk.github.io/-/` с ключом после `#access_key=...`. Код этой страницы находится в `entry/`, публикация — workflow Deploy registry entry. Она загружает Apps Script в изолированном `credentialless` iframe: Google-cookies текущих аккаунтов не отправляются, в том числе вложенным окнам HTML Service. Это обходит ошибку маршрута `/u/1/` до запуска приложения. Поддерживаются актуальные Chrome и Edge; Firefox и Safari не поддерживают этот режим и получают явное сообщение, без загрузки обычного iframe с cookies.

Страница не содержит ключа в публичных файлах. Без правильного URL-фрагмента iframe не создаётся. Готовность показывается только после сообщения от успешно открывшегося Google-приложения; загрузка iframe сама по себе не считается успехом. Скопированная внутри сервиса ссылка ведёт на GitHub Pages. Для встраивания статический HTML Apps Script разрешает iframe через `ALLOWALL`; проверка ключа на каждом RPC остаётся обязательной.

Приложение выполняется от аккаунта, опубликовавшего его (`USER_DEPLOYING`), и разрешает открытие страницы без Google-входа (`ANYONE_ANONYMOUS`). Доступ к данным и действиям даёт случайный ключ в закрытой ссылке. Ролей и списка разрешённых Google-email в приложении больше нет.

Владельцу передаётся полная ссылка вида `https://seainkk.github.io/-/#access_key=КЛЮЧ`. Технический адрес Apps Script остаётся доступен для диагностики. Чтобы передать её коллеге, откройте **«Настройки» → «Доступ к сервису» → «Скопировать закрытую ссылку»**. Все получатели имеют одинаковые рабочие возможности и могут переслать ссылку дальше. Обычный адрес `/exec` без ключа открывает только статический экран с просьбой получить закрытую ссылку.

Ключ состоит из 43 URL-safe символов и генерируется из 32 криптографически случайных байтов. В публичном коде хранится только его SHA-256 verifier; исходного ключа в репозитории нет. Не публикуйте полную ссылку в GitHub Issues, README, общедоступных документах или логах. В URL ключ находится после `#`, не в query-параметре; браузер получает его через `google.script.url.getLocation`. Клиент передаёт ключ в каждом серверном запросе по HTTPS, а сервер проверяет его до обращения к Диску. Значения ключа и OAuth-токенов не возвращаются в данных реестра и не журналируются приложением.

Google-права на файлы не меняются от выдачи ссылки сервиса. **Открытие файла в самом Google Sheets требует прав Google на этот файл.** Редактор внутри сервиса использует проверенный ключ ссылки и права опубликовавшего аккаунта. Папка Диска не становится публичной. Действия внутри приложения выполняются с правами опубликовавшего аккаунта; индивидуального аудита сотрудников нет, новые служебные записи отмечаются общим актором `shared-link`.

## Центр мультиканального аутрича

В верхней панели выберите **«Намшилд»** или **«Нео Сендер»**. У каждого проекта свои сегменты, привязки рассылок, показатели и список почт для мониторинга. Раздел **«Базы»** показывает общий каталог из папки «Исходные базы». В карточке базы или выборки можно отметить один или оба проекта. Фильтр «Проект базы» помогает увидеть нужные материалы.

В **«Настройках»** видны подтверждённый баланс Promouser в USD, лимит автооплаты одного заказа и остаток дневного лимита отправки для выбранных почт текущего проекта в Coldy. Пока окно открыто и вкладка видна, эти данные обновляются примерно раз в минуту. Остаток кредитов организации Coldy для платной валидации в публичном API не предоставляется. [Параметры почтового аккаунта Coldy](https://developer.coldy.ai/docs/api/accounts/get-account/), [метод биллинга Coldy](https://developer.coldy.ai/docs/api/billing/get-transactions/).

Каталог автоматически находит файлы из этой папки и её подпапок. У записи есть название, ссылка на файл, наполнение, статус обработки, ручная проверка формата и подтверждённые связи с сегментами. Для переноса листов в сегмент требуется настоящая Google Таблица.

В таблице **«Исходные базы и выборки»** видны оригинал, рабочая выборка, критерии и сегменты, в которые она добавлена. Подготовленный импорт сохраняет происхождение и список выбранных листов. Для файла с компьютера фиксируются имя и отпечаток содержимого. Старые подтверждённые импорты можно восстановить из журнала, а у выборки без записи указать оригинал и критерии в настройках карточки. У одной исходной базы может быть несколько рабочих выборок. Одна выборка может использоваться в нескольких сегментах.

Внутри реестра два раздела: «Компании» и «ЛПР». Новая база относится к одному выбранному разделу; прежние смешанные базы остаются доступны в обоих. Тип хранится отдельно от содержимого ячеек. Статус: «Сбор», «Готова», «Доработка». Ручная проверка: «Не проверено», «Корректно», «Некорректно». Критерий для компаний — одна строка соответствует компании; для ЛПР — одному человеку. Автоматическая проверка структуры пока не подключена. Изменение наполнения сбрасывает прежнюю проверку, если сотрудник явно не указал новый результат.

Поиск по названию не учитывает регистр и различие е/ё. Выбор раздела и фильтр «Без сегмента» комбинируются с поиском; прежняя смешанная база входит в обе категории. Неизвестные связи не считаются отсутствующими. Несохранённые карточки остаются видимыми с пояснением, даже если не подходят текущему фильтру. Есть счётчик найденных баз и сброс условий.

Отметки сохраняются по ID файла. Переименование не сбрасывает их; исчезнувшие из источника файлы архивируются в служебных данных, сохраняя историю. Одновременное сохранение устаревшей версии отклоняется. Видимый каталог проверяет изменения каждые 30 секунд при доступной версии реестра. Аналитика обновляется примерно раз в минуту. Открытая форма или незавершённое сохранение приостанавливает опрос. Отдельный фоновый обработчик контактов может работать и при закрытом приложении; его включает владелец один раз.

## Загрузка и предпросмотр

Кнопка **«Загрузить базу»** доступна в реестре, в разделе сегментов и в карточке сегмента. Загрузка принимает файл CSV, TSV, XLS, XLSX, ODS до 10 МиБ либо ссылку на доступную для копирования Google Таблицу внутри реестра. Пользователь выбирает существующий или новый сегмент и целевую таблицу «Компании» либо «ЛПР». В карточке сегмент уже выбран. Режим «Только в реестр баз» сохраняет отдельную базу с указанным статусом. Оригинальный файл остаётся на месте.

Загрузка сначала создаёт служебный черновик в отдельной папке корня, вне каталога исходных баз и сегментов. В реестре черновик не появляется. Сначала показывается список исходных листов: по умолчанию отмечены все. В многолистовой книге сотрудник оставляет только рабочие списки и нажимает «Рассчитать предпросмотр»; до этого полное чтение не начинается. Для одного исходного листа предпросмотр рассчитывается автоматически. Выпадающий список образца содержит только отмеченные листы. Изменение отметок сбрасывает прежний результат и требует «Пересчитать предпросмотр»; пустой выбор не допускается. Предпросмотр показывает количество уникальных email, телефонов, Telegram-имён и распознанных компаний из выбранной области, а также контакты, встретившиеся у нескольких компаний. Неполное чтение не выдаётся за окончательный результат.

После подтверждения создаётся новая Google Таблица:

1. **Выбранные исходные листы** — только отмеченные рабочие данные и их оформление. Если выбран один лист, он называется «Исходная база»; при нескольких выбранных листах сохраняются их названия. Результаты формул фиксируются как значения, поэтому новая база не зависит от формул и внешних подключений оригинала.
2. **Email** — один адрес на строку, без повторов. Сохраняются происхождение и сведения о принадлежности; спорные связи помечаются для ручной проверки.
3. **Телефоны и Telegram** — номера и найденные Telegram-имена без повторов. Они находятся в отдельных столбцах; у строки указан тип контакта. Учитываются явные телефонные ссылки, включая скрытые за подписью RichText и HYPERLINK. Числовые ID соцсетей не выдаются за номера телефонов. Если название служебного листа занято исходным, к новому названию добавляется номер.

Если выбран один исходный лист, новая рабочая книга содержит **ровно три вкладки**: «Исходная база», «Email», «Телефоны и Telegram». Полная исходная книга не изменяется. Неотмеченные архивы, прежние выгрузки и сводки не копируются в новую книгу и не добавляют в неё компании, людей или контакты. Из старых отчётов отдельно читается только история проверок и рабочих ограничений, которую можно связать с контактами выбранных листов. Такая история участвует в проверке снимка; неполное или ошибочное чтение истории блокирует подтверждение.

При прямой загрузке первое подтверждение создаёт рабочую базу в каталоге со статусом «Готова». Если пользователь выбрал новый сегмент, создаётся и сам сегмент. Сервис открывает второй предпросмотр с изменениями записей. **«Подтвердить пополнение»** записывает их в одну выбранную таблицу и заполняет её контактные вкладки. После завершения email и телефоны уже доступны со статусами. Закрытие второго предпросмотра оставляет базу в каталоге. Если подготовка была прервана перезагрузкой, журнал подтверждённого задания хранит выбранное назначение.

Email, телефоны и явные Telegram-ссылки ищутся по содержимому ячеек, а не только по заранее известным заголовкам. Поддерживаются заголовки после титула и данные без заголовка. Наличие номера само по себе не подтверждает Telegram. Сканы, картинки с текстом, повреждённые файлы и неоднозначные записи требуют отдельного разбора; гарантии распознавания любого формата нет.

Предпросмотр связан с набором выбранных листов, их данными и прочитанной историей. При изменении выбора, данных или истории требуется новый просмотр. Подтверждённое создание продолжает прежний набор и исходный requestId; менять состав начатой операции нельзя. Подготовка и публикация используют долговечные записи и метки файлов; повтор запроса восстанавливает подтверждённый результат. Неизвестный исход не разрешает слепое создание второй книги. В каталог попадает только законченная книга; ошибка подготовки не выдаётся за успешный импорт. Отмена затрагивает только собственные служебные черновики. Если страницу закрыли во время подтверждённой подготовки, при следующем открытии появляется кнопка «Продолжить» с прежним заданием. Просроченные неподтверждённые черновики очищаются ограниченными порциями.

Произвольные внешние Drive ID не читаются от имени владельца. В режиме закрытой ссылки исходную таблицу сначала добавляют в папку реестра с обычными правами Google либо загружают файлом. Служебная база и внутренние черновики не становятся обычными источниками.

Для прежних источников кнопка «Проверить связи компаний» запускает предварительный анализ. Сравнение с Центром доступно, когда его файл находится в настроенной папке. «Кухни — Центр баз» перенесён в архив, поэтому сейчас показатели сравнения с ним недоступны.

## Редактор таблиц

Кнопка «Работать с таблицей» открывает редактор внутри сервиса: буквы столбцов, номера строк, вкладки листов, адрес ячейки и строка формул. Поддерживаются обычный ввод, формулы, выделение и вставка до 5000 ячеек за операцию, копирование, отмена/повтор, переход к ячейке и добавление строк/столбцов. Для расширенных действий есть ссылка на оригинальный Google Sheets. Новые межфайловые подключения `IMPORTRANGE` настраиваются в Google Sheets; редактор не расширяет границы доступа реестра через формулы.

Изменение сохраняется автоматически после завершения ввода. Индикатор различает сохранение, подтверждённую запись и ошибку. Перед записью сервер сравнивает версии всех затрагиваемых ячеек; обнаруженное чужое изменение не перезаписывается. Неотправленные и неподтверждённые правки остаются в редакторе, их можно скопировать или повторить запрос. Закрытие или переключение листа учитывает очередь сохранений. Повтор подтверждённого запроса не записывает старые данные поверх более поздней правки.

Редактор работает только с Google Таблицами в каталоге исходных баз и рабочих папках сегментов. Служебная таблица и черновики защищены. Каждый запрос заново проверяет ключ и реальное положение файла; при отзыве доступа клиент очищает открытые данные. Все действия внутри редактора выполняются от общего аккаунта приложения. Это отдельный интерфейс сервиса, поддерживающий основные операции с ячейками.

Листы контактов дополняются при изменении исходных данных, а не пересоздаются. Кнопка **«Проверить новые контакты»** сначала дожидается сохранения ячеек, затем добавляет только ещё не учтённые контакты и подготавливает их к ручному запуску валидации. Кнопка сама не создаёт новые платные проверки. В таблице компаний сегмента сначала обновляется связанная база ЛПР. После ввода в исходные листы редактор также запускает обработку с небольшой задержкой.

Во вкладках email и телефонов у контакта есть рабочий статус «новый», «в рассылке» или «фильтр». Новые записи получают «новый». У уже существующих контактов сохраняются заполненные статусы, ручные колонки и результаты валидации. Повторный запуск не создаёт дубликаты. Ранее удалённый пользователем контакт не добавляется обратно при очередном чтении того же источника. Удаление или замена контакта в исходнике сохраняет прежнюю запись в рабочем списке.

Кнопка и настройки валидации находятся **в редакторе сервиса**. Код не устанавливает меню или скрипт в каждую Google Таблицу. Для правок, внесённых прямо на сайте Google Sheets, используется общий фоновый обработчик.

## Сегменты

В новом сегменте основной лист компаний начинается с ID компании и полей справочника по образцу «Кухни СПБ + МСК». Это названия, категории, регионы и области, населённые пункты, полные адреса, мобильные и городские телефоны, email, Telegram, WhatsApp, ВКонтакте, Одноклассники, сайты, Max, число филиалов, почтовые индексы и дата парсинга. Можно загрузить часть полей в любом порядке. В прежних таблицах недостающие поля добавляются справа при пополнении из справочника. При совпадении компании новые категории и адреса дополняют её строку. Для числа филиалов и даты сохраняется первое заполненное значение.

Таблица ЛПР хранит ФИО, должность, личные контакты и сведения о компании. Человек с известными ФИО или должностью появляется в базе даже без телефона и email. ID компании при пополнении только ЛПР проставляется, когда исходные данные однозначно указывают на существующую компанию сегмента.

Каждая непосредственная подпапка «Аутричи» — отдельный сегмент. В приложении сегменты показаны в разделах «Партнерка» и «Клиенты» со статусом, каналами, показателями и ссылками. «Веб-студии» по умолчанию относятся к «Партнерке», остальные существующие сегменты — к «Клиентам». Выбранный в редакторе раздел сохраняется по ID папки.

«Добавить сегмент» создаёт папку и две Google Таблицы: `Название: компании` и `Название: ЛПР`. Исходные базы необязательны — можно заполнить сегмент позже. «Редактировать сегмент» позволяет изменить название папки и назначенных файлов, добавить базы из реестра.

Кнопка **«Пополнить базы»** позволяет выбрать до пяти уже готовых баз из реестра для распределения записей по двум файлам сегмента. Загрузка с компьютера из этого редактора возвращает пользователя к его выбору после подготовки файла. В сегмент допускаются базы с сохранённым статусом **«Готова»**. Сервер повторно проверяет расположение и состояние источников при записи и продолжении задания.

Перед переносом показывается отдельный предпросмотр: сколько компаний и ЛПР будет добавлено или дополнено и что требует проверки. Столбцы распознаются и приводятся к общей схеме автоматически. Для прежних клиентов сохраняется явный выбор назначения листа и наличия заголовка.

В файле компаний сегмента ведётся одна основная таблица: идентификаторы и название компании, сайт, город, общие контакты, сведения о найденных ЛПР, источники и статус. В связанном файле ЛПР — компания, ФИО, должность, контакты, источники и статус. Дополнительные подробности остаются в исходных файлах реестра. Прежние рабочие листы не удаляются.

Повторное пополнение объединяет распознанные записи, дополняет контакты и сохраняет заполненные рабочие статусы. Компания не объединяется с другой только из-за похожего названия или общего телефона: противоречивые ИНН, ОГРН и другие неоднозначные связи попадают в список проверки. Строки с контактами без определённой компании сохраняются с задачей уточнить компанию.

При общем пополнении ЛПР из таблицы компаний добавляются в связанную таблицу **даже без email и телефона**. Такие записи получают статус «Найти контакты» либо «Найти ФИО и контакты». После подтверждённой записи ЛПР в исходной строке реестра и таблице компаний появляется отметка **«Перенесено в ЛПР»**. При прямой загрузке в «Компании» сведения о человеке остаются в этом файле для последующего переноса при проверке новых контактов.

В новых рабочих списках основные поля идут в порядке образца. Email содержит рабочий статус, комментарий, число адресов компании, исходные строки, компанию/ЛПР, адрес, валидацию, провайдера, сайты и ID компании. Телефонный список содержит статус, исходные строки, компанию/ЛПР, номер, ID и имя пользователя Telegram, давность активности, сайты и ID компании. За этими полями могут следовать служебные колонки. Для однозначной компании один ID связывает основную запись с контактами. Общий контакт требует проверки владельца.

Готовая трёхлистовая выборка образца «основной лист + Мобильные телефоны + Email» распознаётся по составу книги и заголовкам отчётов. При пополнении из такой выборки учитываются контакты из её рабочих списков и указанные исходные строки. Сегмент сохраняет прежние статусы, результаты проверок и ссылки на строки в поле «История контакта». Противоречивую историю валидации сервис отмечает для ручной проверки. Заполненные вручную данные сегмента сохраняются при дальнейших пополнениях.

Базу ЛПР можно пополнять и отдельными базами реестра. Новые строки, введённые непосредственно в основной лист компаний сегмента, обрабатываются той же кнопкой или фоновым обработчиком. Изменения старого источника реестра передаются в сегмент повторным пополнением из этого источника; одна связь с сегментом не означает постоянную двустороннюю синхронизацию.

## Promouser: только новые контакты

Откройте **«Настройки» → «Настроить Promouser»**. Здесь можно сохранить общий API-ключ, настроить лимит и проверить баланс. В редакторе таблицы те же настройки доступны через **«Валидация»**. Ключ сохраняется в закрытых свойствах Apps Script (`Script Properties`) и доступен серверу. Запросы идут напрямую из Apps Script; доступ со стороны Promouser должен разрешать этот источник запросов.

Проверка использует услугу 17 для email и 6 для подробного Telegram по телефону. Email обрабатываются выбранным валидатором: по умолчанию Promouser, при выборе Coldy новые email не ставятся в платную проверку Promouser. Телефоны и Telegram остаются в Promouser. В редакторе сначала открывают предпросмотр новых email или телефонов, затем нажимают «Запустить проверку…». Локальное распределение контактов и таймер не дают разрешения создавать новые заказы. Только ручной запуск одобряет показанный набор; после него заказы создаются для расчёта цены, без `force`. При лимите автооплаты **0** стоимость требует подтверждения в интерфейсе. Положительный лимит разрешает автоматическую оплату каждого заказа в его пределах; крупная база может разбиваться на несколько заказов. Для этого проекта согласовано правило: **после ручного запуска до 5 USD за отдельный заказ — автоматически, выше — ручное подтверждение**. Это настройка подключения, а не вшитое значение по умолчанию. Запрос цены перед оплатой обновляется, но API Promouser не принимает параметр максимальной суммы, поэтому атомарно ограничить изменившуюся у провайдера цену нельзя.

В лист Email добавляются результат, дата проверки, провайдер и номер заказа. В лист телефонов — результат, дата, номер заказа, **`ID_TG`, `Nickname_TG`, `Active_days_ago`** и отметка «Для Telegram». Подходящим для Telegram считается подтверждённый аккаунт с положительным ID и известной активностью не более 30 дней назад. Скрытые или неизвестные сведения требуют проверки; одно имя Telegram без телефона не отправляется как номер.

**Уже проверенные контакты не отправляются повторно**, включая невалидные и завершённые результаты с неопределённым ответом. Их строки и заметки не переписываются. Общий кеш позволяет использовать известный результат в другой базе без новой платной проверки. Для незавершённого заказа сохраняется его идентификатор: потеря ответа не вызывает слепой повтор отправки или оплаты.

При переносе старой истории email-вердикт относится к email, а Telegram-результат — к соответствующему номеру. Системные заметки связывают проверку с точным контактом: замена адреса или номера в старой строке не переносит прежний результат на новое значение. Противоречивая история, ручные исключения и прежнее участие в рассылке дают завершённую отметку «Проверить историю контакта»: повторная платная проверка пропускается, а загрузка в Coldy блокируется. Простая правка ячейки не снимает общий признак проверки истории; отдельный интерфейс согласованного повторного включения ещё не реализован. `Active_days_ago` сохраняет ответ на момент последней проверки, а не текущий онлайн. Кнопка проверки новых контактов не обновляет возраст старых результатов.

Один запрос к тому же заказу выполняется не чаще раза в 5 секунд, проверка готовности — раза в 15 секунд. Ожидание результата, отсутствие баланса или ошибка связи не выдаются за валидный контакт. Ручная чистка и разметка отделов остаются отдельными этапами. Подключение Promouser не запускает рассылку.

## Coldy: подключение, загрузка и аналитика

Откройте **«Настройки» → «Настроить Coldy»**. API-ключ вводится в поле пароля, очищается при отправке, закрытии и отзыве доступа; сервер никогда не возвращает его в настройках. Там же выбирается валидатор новых email — Promouser или Coldy. Telegram по телефону продолжает проверяться через Promouser. Кнопка «Проверить подключение» подтверждает ключ одним бесплатным запросом. В настройках сначала появляются статус подключения и время проверки. Дневные лимиты выбранных почт загружаются отдельно.

Адаптер использует официальный `https://developer.coldy.ai/api/v1` и фиксированный список маршрутов. Ключ передаётся только сервером в заголовке `Authorization`; произвольные адреса и перенаправления запрещены. JSON-журналы, результаты и снимки кампаний привязаны к корню реестра и текущему ключу. Смена ключа останавливает работу со старыми заданиями без слепого повтора в другом аккаунте.

В разделе **«Сегменты → Рассылки»** сотрудник привязывает существующую кампанию Coldy к сегменту и выбирает управляемые Email-листы компаний, ЛПР или оба источника. Одну кампанию нельзя привязать сразу к двум сегментам, чтобы её статистика не учитывалась в двух местах. Перед загрузкой показываются количество новых валидных адресов, уже загруженных, непроверенных, невалидных и спорных контактов. По умолчанию принимаются только завершённые положительные проверки без спорной принадлежности; `accept_all`, `disposable`, неизвестные и невалидные результаты не допускаются.

Ручная загрузка начинается после подтверждения предпросмотра. Автозагрузка новых валидных адресов требует отдельного сохранённого разрешения в привязке и установленного общего таймера. Она не разрешает автоматическую валидацию новых адресов. Для активной кампании отдельно подтверждается, что добавление контактов может сразу вызвать отправку писем. Без этого разрешения загрузка в Active блокируется; используются Draft или Paused. API создания и активации кампаний в реестр не включены.

Перед каждым удалённым изменением сохраняется задание и исходный `requestId`. При неизвестном результате сначала проверяется существование точных email в выбранной кампании; POST не повторяется вслепую. После подтверждения заполняются только служебные колонки «Coldy: рассылки», «Coldy: статус», «Coldy: дата загрузки». Пользовательские колонки и статусы не перезаписываются. Дубль в аккаунте Coldy не считается подтверждением загрузки в выбранную кампанию; подтверждённая загрузка сама по себе не доказывает отправку письма.

**Валидация Coldy запускается вручную** в редакторе таблицы: предпросмотр новых email → подтверждение расхода кредитов → запуск. Один пакет содержит до 500 уникальных email. Долговечный `Idempotency-Key` сохраняется до платного запроса. Завершённый результат любого валидатора, включая отрицательный, рискованный, неизвестный и ручное исключение, пропускается; действующие резервации Promouser и Coldy используют общий кеш и блокировку. Старые результаты Promouser сохраняются. «Валидатор» обозначает сервис проверки; «Провайдер» остаётся почтовым провайдером. Кредиты Coldy не ограничиваются настройкой 5 USD Promouser; автоматический запуск новых проверок Coldy отключён.

Экран рассылок читает сохранённую аналитику; **«Обновить данные Coldy»** запрашивает текущие значения у API. Используются `total_sent` для отправлений, `replies_emails` для ответов и `summary.interested` для лидов. Показатель ответов используется в смысле API, без предположения об уникальных людях. Суммы считаются по привязанным кампаниям; если хотя бы одно слагаемое неизвестно, соответствующий итог остаётся `null` и показывается «—». Сохраняются даты обновления и сведения о кеше. Неизвестные метрики NSA не заменяются нулями. Сохранение API-ключа и успешные тесты с моками не подтверждают живой доступ к аккаунту Coldy.

## Аналитика и инфраструктура проекта

Вкладка **«Аналитика»** показывает сохранённые рассылки выбранного сегмента. Кнопка **«Добавить рассылку»** открывает поиск по названию, ссылке или ID. Открытый раздел обновляет показатели примерно раз в минуту. Здесь показаны их состояния, отправления, ответы, лиды и итог по сегменту. Неизвестные показатели отображаются прочерком. Выбор использует те же привязки, что экран «Сегменты → Рассылки»; настройки загрузки у неизменённых связей сохраняются. Кампанию, принадлежащую другому сегменту, нельзя выбрать второй раз. Снятие выбора удаляет связь, включая её автозагрузку, а не контакты кампании.

Вкладка **«Инфраструктура»** показывает почтовый пул текущего проекта. В строке отправителя видны занятость, активные рассылки, их сегменты и ближайший перерыв между окнами отправки. В расписании указаны дни, часы и часовой пояс. Coldy не предоставляет плановую дату завершения кампании. Нажмите **«Выбрать почты»**, чтобы изменить пул для команды проекта, или **«Обновить из Coldy»**, чтобы обновить имена и назначения. Обновление пула сначала получает назначения выбранных ящиков, затем запрашивает расписания привязанных активных кампаний параллельно, до пяти за раз. У ранее полученного расписания видны время и состояние обновления. Активная кампания вне выбора обозначается как другая рассылка. Подробные сведения по каждому ящику запрашиваются отдельно кнопкой **«Обновить диагностику»** в блоке **«Состояние ящиков и счётчики Coldy»**. Там видны подключения, лимиты, счётчики и дата проверки.

При выборе почт точный известный адрес находится в сохранённом списке. После явного поиска по имени или части адреса сервис может до минуты искать по разным фразам в уже полученном ответе Coldy. В браузер отправляются выбранные почты и до 50 совпадений.

Сначала доступны сохранённые данные. Кнопки обновления запрашивают сведения заново; большой список обрабатывается частями с сохранённым продолжением. При временной ошибке старые данные остаются видимыми с отметкой времени и предупреждением. Ключ хранится только в общих серверных настройках, секреты почтовых подключений в интерфейс не копируются.

## Обработка изменений при закрытом приложении

В окне **«Подключение Promouser»** есть кнопка **«Включить обработку изменений в Google Таблицах»**. Она создаёт один общий таймер Apps Script примерно раз в 5 минут. Он обходит подключённые книги, дополняет списки контактов, переносит ЛПР из компаний сегмента, продолжает ранее разрешённые проверки и выполняет явно включённую автозагрузку валидных email в Coldy. Новые платные проверки обоих провайдеров запускаются только вручную после предпросмотра. Крупная очередь продолжается следующими порциями.

Если Google требует новое разрешение, владелец один раз открывает существующий проект Apps Script, обновляет редактор, выбирает файл **`ContactAutomation.gs`** и запускает видимую функцию **`authorizeGoogleAccess`**. Она проверяет все уже объявленные разрешения Google, включая частично выданный доступ. После подтверждения нужно вернуться в сервис; для фоновой обработки отдельно нажать **«Включить обработку изменений в Google Таблицах»**. Функция разрешения не меняет данные, ключи и таймеры. Служебная `setupContactAutomation_` скрыта из списка редактора. До настройки таймера ручная кнопка сервиса остаётся доступна. Установка таймера сама по себе не разрешает начинать новые платные проверки.

## Статусы и рассылки

- «Нет контактов» — проверенные листы пусты с учётом указанного заголовка.
- «Подготовка» — есть хотя бы одна строка данных.
- «В работе» предусмотрен для будущей проверки контактов со статусом «запущен».

Сервер читает наличие контактов ограниченными порциями; эта аналитика не передаёт значения ячеек в браузер. Пустые отображаемые значения формул не считаются контактами. У старого листа с одной заполненной строкой и неизвестной настройкой заголовка статус остаётся неопределённым. Ошибка проверки не превращается в ложное отсутствие контактов.

Email, Telegram и Ретаргетинг по умолчанию красные; проверка запусков ещё не подключена. Показатели в работе пока показывают прочерки. «Рассылки» открывает экран Coldy/email и NSA/Telegram со списками, показателями отправлений, ответов и лидов и итогами. Coldy подключается через API и показывает данные привязанных к сегменту кампаний. NSA остаётся неподключённым; ручного ввода и вымышленных кампаний или нулей нет. Раздел «Ретаргетинг» ждёт согласования структуры.

## Служебные данные и границы

Служебная Google Таблица находится непосредственно в корне реестра. До чтения и записи проверяются ID, MIME и реальное положение, перед изменениями — права редактора. Используются листы `SourceBases` (13 столбцов, наполнение JSON в M), `SourceBaseSegments`, `SegmentTables`, `SegmentLoads`, а для общих результатов проверок — `ValidationCache`. Долговечные задания, состояние контактов, очереди Promouser и Coldy, связи с кампаниями и сохранённая аналитика хранятся в отдельных служебных файлах внутри корня реестра, вне пользовательского каталога и папок сегментов. API-ключи провайдеров хранятся только в `Script Properties` и не записываются в служебные JSON. Миграция прежних схем сохраняет отметки, версии и связи и выполняется под общей блокировкой.

Только `doGet`, `callApp` и форма `uploadSourceBase` являются публичными функциями. Бизнес-обработчики заканчиваются `_` и недоступны прямому `google.script.run`. Dispatcher содержит фиксированный список методов. Проверенный контекст существует только на время одного вызова и снимается в `finally`; подмена клиента или обход кнопки не заменяют ключ. Списки `ALLOWED_EMAILS` / `ADMIN_EMAILS` предыдущего режима больше не используются и автоматически не удаляются.

При необходимости владелец может заменить verifier свойством `SHARED_ACCESS_KEY_SHA256` в Script Properties. Значение — SHA-256 нового случайного ключа в Base64URL без `=`. Это отзывает старые ссылки, включая последующие запросы из открытых вкладок. Пустое или повреждённое свойство блокирует доступ. Без свойства используется verifier из `Config.gs`; исходный ключ не восстанавливается по хешу, поэтому полную ссылку нужно сохранить приватно.

Лимиты каталога: до 5000 файлов и 5000 строк на основные служебные листы. Прежний анализ «Проверить состав» ограничен 80 файлами, 240 листами, 100000 ячейками и 20 секундами на запрос; превышение отображается как неполная проверка. Новая обработка контактов и импорт сегментов имеют отдельные лимиты и продолжаемые задания. Квоты Google расходуются от аккаунта, опубликовавшего приложение.

## Отклик интерфейса

Форма сегмента использует уже загруженный каталог. При переходе между разделами успешные чтения повторно используются до 30 секунд; кнопка обновления запрашивает данные заново. При первом открытии сегментов сначала приходят папки и ссылки на таблицы без чтения контактных строк; статусы догружаются отдельно. Пока проверка не завершена, статус остаётся неопределённым, а не превращается в «Нет контактов». Перед любым изменением сервер заново проверяет расположение файлов, готовность баз и их версии.

После подтверждения создания или импорта результат сразу появляется в списке, а полная проверка выполняется отдельно. Открытие форм и ввод не блокируются независимыми фоновыми чтениями. Изменения выполняются последовательно; отдельные чтения могут идти параллельно с ограничением числа запросов. Неизвестный результат записи сохраняет прежнюю защиту от повторного создания файлов и листов.

Для карточек баз сервис одним запросом Google Sheets читает значения и проверяет наличие формул на четырёх служебных листах, когда они есть и размер данных позволяет. Листы с датами или неподдержанным типом ячейки читаются отдельно. Для связей с сегментами нужны только названия их папок. Для привязанной рассылки Coldy сервис параллельно запрашивает её текущие параметры и сводную аналитику.

Журнал листов читается один раз на запрос списка сегментов. Проверка наличия контактов начинает с одной строки данных и переходит к ограниченным блокам, только если она пуста. Между запросами серверный снимок не сохраняется.

Редактор получает метаданные книги и первые 80 × 50 ячеек одним запросом. Ячейки содержат те же версии для обнаружения конфликтов; результаты чтения не становятся межзапросным кешем ячеек. Настройки обработки контактов не задерживают первое отображение таблицы. Создание Google Таблиц, копирование листов и полный анализ большого исходника всё ещё требуют ответа Google и могут занимать время.

## Разработка и публикация

Подробности в [DEPLOYMENT.md](DEPLOYMENT.md). Проверки: `npm ci`, `npm run check`, `npm test`. Новых npm-зависимостей нет. Apps Script получает только `src/`.

Код в `main` проверяется и публикуется GitHub Actions → clasp. Прежний Deployment ID и базовый URL сохраняются. Скрипт дополнительно читает фактическую конфигурацию Google API и подтверждает анонимный доступ и выполнение от владельца; зелёные unit-тесты сами по себе не подтверждают эти настройки.

Тесты подменяют Google API. Проверки интерфейса с управляемыми задержками: `python tests/browser/performance_client.py`, `python tests/browser/navigation_performance.py`, `python tests/browser/contact_preview_client.py`, `python tests/browser/prepared_registry_client.py` `python tests/browser/grid_client.py`, `python tests/browser/contact_workspace_client.py`, `python tests/browser/coldy_client.py` и `python tests/browser/segment_workspace_client.py` (требуются Playwright Python и Chromium, рабочие файлы не затрагиваются). Отдельная браузерная проверка после публикации нужна для реального анонимного входа с URL-фрагментом. Тестовые контакты в рабочие файлы не добавляются. В `extension/` остаётся отдельный прежний прототип; он не требуется приложению и не опубликован в Chrome Web Store.
